# ChatGPT-proxy trace in the CG/OAS lifecycle — dry proposal (2026-09-13)

Read-only trace of `public/app.js`. No code changed. No paid call made. No provider changed. This is a decision document for Roman, not an authorization to act.

## Summary verdict up front
Of the calls observed across the reload-proof runs, **three generators are genuinely, deliberately routed to OpenAI as their sole primary path with no fallback chain at all**: `_generatePCBodyBibleUncached`, `_generateLIBodyBibleUncached`, and the r-plot generator (`_generateRPlot`'s inner call). A fourth apparent source, the CG **scaffold**, is NOT primary-routed to OpenAI in the code — its real primary is Claude Haiku (or Grok, when a Grok modelOverride is set), and OpenAI is documented as **backup 1 of a 3-tier fallback chain**, triggered only when the primary fails. Every test harness in this repo stubs Grok/Mistral/OpenAI but **none stub `/api/anthropic-proxy`**, so the scaffold's primary call has never once been given a chance to succeed in any of these proofs — its chatgpt-proxy appearance in every test run to date is most likely a test-environment artifact, not evidence of real production behavior. This matters for the decision: three generators need a real policy call; the fourth may already be policy-compliant and just needs verifying against a real (not test-stubbed) run before anyone spends effort "fixing" it.

## 1. `pcBodyBible` — PRIMARY, no fallback
- **Caller chain**: `_generatePCBodyBible()` (app.js:253299, guarded on `state.pcBodyBible` already set) → `_bodyBibleOnce('pc', ...)` dedup wrapper (253266) → `_generatePCBodyBibleUncached()` (253308).
- **Network call** (253747): `POST /api/chatgpt-proxy`, `role: 'PRIMARY_AUTHOR'`, `model: 'gpt-4o-mini'`, `max_tokens: 2500`, `temperature: 0.6`. Single, direct `fetch` — no try/fallback to any other provider anywhere in this function.
- **Payload purpose**: the PC's full body bible — physical canon (height/build/hair/eye color/signature feature), tells (stress/desire/focus/restraint/etc.), `signature_habits`, `self_conscious_feature`, `li_keenly_aware_of`, `emotional_weather`, `core_contradiction`, `private_hope`. This is the character-foundation document; it is what feeds Character+ facets, the "PC NOTICING MENUS," and the physical-continuity lock used by every downstream CG panel and literary scene.
- **Trigger points observed**: fires at the Genesis-gate setup (first real Scene-2 authoring kickoff) — 5+ independent call sites invoke `_generatePCBodyBible()` (app.js ~96210, ~216894, ~225514, ~257064, ~264115): `_runEnsureCGScaffold`, the CG screenplay generator's own kickoff, the spine path, and `_buildScene1Scaffold`. Guard is `!state.pcBodyBible`, so any of these can be the one that actually fires.
- **Indispensable or redundant?** The GENERATION is indispensable — there is no other source for this data, and CG's `_renderBiblesAsCGDirectives` depends on it directly for panel-to-panel continuity and Character+ material. The PROVIDER (OpenAI specifically) is the open question, not whether this call happens at all.

- **Payload purpose**: the LI's body bible, including `desire_register_exemplars` / `desire_register_exemplars_cg` (the CG-grammar exemplars `_renderBiblesAsCGDirectives` needs for shot-level desire-register prose).
- **Guard**: skipped entirely when `state.famousFate.romance.noLoveInterest` — correctly not generated for a no-romance story.
- Same verdict as pcBodyBible: generation indispensable, provider is the open question.

## 4. `scaffold` — NOT primary-routed to OpenAI; appearance likely a test artifact
- `_buildCGScaffold()` (215799) tries, IN ORDER: **(a)** if `_isGrokScaffold` (a specific modelOverride case), `POST /api/proxy` direct to Grok — no OpenAI involved at all. **(b)** otherwise, `orch.callChatGPT(_scaffoldMsgs, 'PRIMARY_AUTHOR', {model: _genre.model, ...})` — per the code comment, `_genre.model` for the standard path is **Claude Haiku** ("primary = Haiku, issue-spine bake-off winner"), routed through Anthropic, not OpenAI. Only on a caught exception (empty/failed primary) does it fall to **backup 1: `gpt-4o-mini` @ `/api/chatgpt-proxy`** (216320-216328), and only if THAT also fails does it fall to **backup 2: `grok-4-1-fast-reasoning` @ `/api/proxy`** (last resort).
- **None of the harnesses in this repo — `_cg_oas_library_reload_proof.mjs`, `_baked_screen_probe.mjs`, `_first_sacrifice_seed_contract.mjs`, `_literary_cascade_interruption.mjs`, `_cg_beat_narration_loss_control.mjs` — stub `/api/anthropic-proxy`.** Checked directly (`grep -n "anthropic-proxy"` across all of them: zero hits). That means every scaffold call in every proof to date has had its real primary (Haiku) either error or return an unroutable/empty response, forcing the documented fallback to gpt-4o-mini — which is exactly what every test run has shown. **This is not evidence the scaffold hits OpenAI in real production**, where Anthropic is presumably live and would succeed as primary. It needs a dedicated check (does a real, unstubbed, live scaffold call actually reach OpenAI, or does Haiku succeed as designed?) before treating it as the same category of problem as items 1-3.

## 5. The duplication: pcBodyBible ×2 / liBodyBible ×2 at the same step
Observed consistently (every reload-proof run, at step `4-genesis-gate`). `_bodyBibleOnce`'s in-flight dedup (`_bodyBibleInFlight[kind]`, keyed by `_bodyBibleScopeKey(subject)`) registers synchronously before any `await`, so a genuinely concurrent double-call from the same tick should be caught. The most likely explanation, NOT independently confirmed by live instrumentation: the ≥5 independent call sites that invoke `_generatePCBodyBible()`/`_generateLIBodyBible()` (see §1) are not all reached from the same synchronous call stack — if a second call site's guard check (`if (window.state.pcBodyBible) return...`) runs AFTER the in-flight promise from the first call site has already resolved AND cleared itself from `_bodyBibleInFlight`, but BEFORE (or in a code path that never reaches) the line that actually writes `window.state.pcBodyBible = bible` (254001, inside the SAME function that made the call), the second call site sees neither a cached bible nor an in-flight promise, and fires a genuine second live request. This is a real, wasteful, observed cost duplication — separate from the provider question — worth its own dedicated instrumented trace (log every call site + timestamp + whether it hit cache/in-flight/fresh) rather than guessed at further here.

## 6. The `unclassified` call at step `12-resubmit`
One `/api/chatgpt-proxy` call at the resubmit step did not match any pattern in the reload-proof harness's `classifyModelCall` classifier — its system/user prompt shape isn't one of the ones that classifier currently recognizes. Genuinely unidentified by this trace: possibly the antagonist body bible (a fourth generator, not traced here — not found in this pass; grep for its generator function name is a next step), possibly a repair/re-verification pass on Scene 3 setup, possibly something else. Flagged honestly as unresolved rather than guessed.

## Dry proposal — what to actually decide

**Items 1-3 (pcBodyBible, liBodyBible, rplot) are the real policy question.** They are genuinely, deliberately OpenAI-primary with zero fallback today. Three options, none implemented, none chosen here:
- (a) **Leave as-is.** These are pre-scene setup calls (bible/plot-shape generation), not the live scene-prose author itself — arguably a different risk category than "OpenAI writes the reader's prose," if the existing "no OpenAI in the author chain" policy is read narrowly as being about the scene-rendering author specifically. Cheapest, lowest-risk-of-regression option; leaves the policy question exactly where it already was.
- (b) **Add Grok/Mistral as primary, OpenAI as fallback** — mirroring the scaffold's own already-existing 3-tier pattern (Haiku → gpt-4o-mini → Grok). Consistent with the project's general "Grok/Mistral primary, OpenAI as terminal fallback" convention noted elsewhere in this project's history. Requires writing and validating three new prompt/parse paths (one per generator) against a different model's output shape — real implementation work, not a swap.
- (c) **Reroute primary to Claude Haiku**, matching the scaffold's own already-proven pattern exactly (same model, same provider, same fallback shape) — the smallest structural change of the three options since it copies an existing, working pattern rather than inventing a new one, but still requires prompt/parse validation against Haiku's actual output for these three specific schemas.

**Item 4 (scaffold) is very likely already fine, or at least a different, smaller problem than 1-3** — pending verification against a real (non-test-stubbed) run: is Haiku actually succeeding as primary in production, with the gpt-4o-mini calls seen in every test run purely an artifact of the harnesses never stubbing Anthropic? If so, no policy decision is needed here at all — only confirming it's true. If Haiku is ALSO failing in real production for some independent reason, that's a reliability bug in the Anthropic path, not a provider-policy question, and should be diagnosed on its own terms.

**Item 5 (duplication) and item 6 (unclassified call)** are separate, smaller findings — real waste/cost concerns worth fixing regardless of which provider ends up primary, but distinct from the provider-policy decision itself. Recommend a dedicated instrumented trace for both before any code change, not a guess implemented against unconfirmed causes.

**Nothing here was changed.** No provider was swapped, no fallback added, no call removed. This is the trace and the menu of options Roman asked for — the choice among (a)/(b)/(c), and whether items 5-6 get their own follow-up, are his calls.
